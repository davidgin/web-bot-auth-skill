# Policy decisions

Settle these with the user before wiring anything in. Each lists the default in `Policy` or the resolver, the reason for it, and what changing it costs.

## 1. Which operators are trusted

Only allowlisted identifiers produce `verified`. In -01 the identifier of an agent is the `Signature-Agent` URL it publishes its keys at (-01 section 4.1); `Result.operator` carries it, normalized. Options:

- **Static keys** (`StaticKeyResolver`): keys pasted into config, keyed by agent URL (stored as its normalized identifier) or `None` for agents that send no `Signature-Agent`. Simplest and no network access, but rotation is a config change. Two entries that normalize to one identifier raise `ValueError`.
- **Directory fetch** (`DirectoryKeyResolver`): server configuration selects the directory. Every allowlist entry is a full HTTPS URL, for example `DirectoryKeyResolver(["https://agent.example/operator/keys.json?version=2"])`. Its identifier is the normalized URL without the query (`https://agent.example/operator/keys.json`, -01 section 5.5: one key set must not yield an identifier per query spelling), and the fetch URL is that identifier plus the entry's normalized query. Normalization lowercases scheme and host, removes the default port, decodes unreserved percent-encodings, uppercases the hex of the others and removes dot segments (`normalize_agent_url` shows the result). Fragments, userinfo, non-HTTPS, non-ASCII and malformed URLs are rejected with `ValueError`. Two entries with the same identifier and different fetch URLs (for example two queries) raise `ValueError` naming the identifier, in any order; identical ones are accepted.

**Bare origins are a deviation from -01.** -01 sections 4.1 and 4.4 say the identifier is the URL the verifier fetched. An entry whose path is `/` (`https://agent.example`) instead fetches `https://agent.example/.well-known/http-message-signatures-directory` (plus any configured query) and keeps `https://agent.example/` as the identifier. Reason: the well-known path is reserved for the domain operator (-01 section 4.5), so what it serves endorses the bare origin as strongly as it endorses the well-known URL, and deployed agents and -01's own examples send bare origins. The cost is that the identifier and the fetched URL differ, and that **`https://agent.example/` and `https://agent.example/.well-known/http-message-signatures-directory` are different identifiers** (-01 section 5.5 compares octets). An agent that sends the explicit well-known URL does not match a bare-origin entry and gets `unknown_operator`; an agent that sends the bare origin does not match an explicit well-known entry. When an agent may send either, allowlist both. Two such entries fetch the same document twice and keep two caches (no fetch coalescing, which -01 Appendix C.3 only suggests).

The resolver caches successful fetches for the `Cache-Control` max-age (clamped to 5 min-24 h). Unknown `keyid` values can trigger rotation refetches, but all fetch attempts share a per-identifier limit (once a minute by default), even with an empty cache, a timeout or a malformed response (-01 Appendix C.3, C.5). Concurrent requests share this limit within each resolver instance. A failed refresh preserves the last good copy for an allowlisted identifier: a directory that fails to resolve is not evidence and must not evict it (-01 section 6.10). When an allowlisted identifier has no fresh directory (first fetch in flight or failed, or the cache expired and the refresh failed or was rate-limited) and the keyid is not in the stale copy, the result is `unknown_operator` with reason `key directory unavailable`, not `invalid` (-01 Appendix C.1 "unverified"): that is not evidence of a bad signature, and the caller treats it as unsigned and a later request succeeds once the limit allows a fetch. A keyid missing from a fresh cached directory stays `invalid`, because a directory that resolves without the key is evidence that it was removed (-01 section 6.10). Concurrent requests during an in-flight first fetch do not wait for it. During a directory outage, forged requests claiming an allowlisted identifier are also reported as `unknown_operator` rather than hostile; that loses detection signal but never grants access.

Request `Signature-Agent` values only select among identifiers you configured; they never choose a fetch URL, query or path. A claimed URL that is not allowlisted gets no fetch. Allowlist changes:

- Removing an identifier from `resolver.allowlist` at runtime revokes trust immediately. A cached key may then resolve only as `signed_untrusted` until its cache entry expires, after which it is unavailable. Removing trust does not trigger another fetch.
- `resolver.allowlist.add`, `update` and `|=` accept only values that are already normalized (`value == normalize_agent_url(value)`) and raise `ValueError` naming the normalized form otherwise. This makes the 0.1.1 idiom `add("https://host")` (without the trailing slash) fail loudly instead of never matching: write `add("https://host/")`. A runtime-added identifier fetches itself, or the well-known URL if its path is `/`; it cannot carry a custom query. To add a fetch query or change a directory URL, construct a new resolver with the complete configuration. Other set operations on the allowlist are not guarded; do not use them, and do not assign a new set.
- Ask who approves additions to the allowlist; this is a trust decision, not a technical one.

**Request-side members that are ignored.** A `Signature-Agent` member that carries parameters is ignored (-01 section 5.2.1 MUST). So is a signature whose covered `signature-agent` components are all keyed to a label other than its own: an intermediary may relabel the `Signature` member (RFC 9421 section 7.2.5) but cannot change the covered member key (-01 section 6.6.1), and -01 section 5.2.1 forbids crediting a member the signature does not cover under its own label. In both cases the key is looked up as for a request with no header (`operator` is `None`), `claimed_agent` stays `None`, and the outcome follows the resolver: `signed_untrusted` for `DirectoryKeyResolver` when the key is in an unattributed list (below), otherwise `unknown_operator`; for `StaticKeyResolver`, whatever its `None` entry gives. It is never `invalid` because of the label mismatch.

**Keys from lists you did not fetch (-01 section 5.5.3).** A verifier must not attribute a request to a URL on the strength of redistributed key material unless it carries a valid directory response signature (-01 Appendix B), which this verifier does not check. So:

- `add_untrusted_directory(url, data)` (`fetched=False`, the default): the keys verify signatures, but are credited to no URL. The result is `signed_untrusted` with `operator=None`, never `verified`, and `keyid` is the identifier (-01 section 4.3). `url` is only the replacement key: adding the same `url` again replaces that list (-01 section 4.4, the newer pair wins), and each list expires after `ttl`.
- `add_untrusted_directory(url, data, fetched=True)`: use it only when your own background job fetched `url` over TLS with `safe_fetch_directory` (a verifier or control plane polling a directory is resolving it, not redistributing, -01 section 5.5.3). The keys are attributed to the normalized `url` and resolve as `signed_untrusted` with `operator` set; they are never `verified`. An allowlisted `url` raises `ValueError` for both values: allowlisted URLs are fetched, not added.
- **Removal wins.** When the claimed identifier is allowlisted and has a fresh directory that lacks the key, lists are not consulted and the result stays `invalid` (-01 sections 4.4 and 6.10). Lists are consulted only when the identifier is not allowlisted or its directory is unavailable.

If the user wants to recognize agents beyond the allowlist, do it in a background job that calls `safe_fetch_directory` and `add_untrusted_directory(..., fetched=True)`; those agents come back as `signed_untrusted`, never `verified`.

**Draft scope.** This skill targets `draft-ietf-webbotauth-httpsig-protocol-01`. It follows section 4.1 (the `Signature-Agent` URL is the identifier; a claim becomes an identity only once resolved), section 4.4 (never attribute to a URL without making the key-to-URL association; newer pair wins), section 5.4 (key lookup is keyed on the (URL, key) pair, never on the keyid alone), section 5.5 (identifier compared after normalization, query dropped; 200 only, no redirects), section 5.5.3 (redistributed keys carry no URL) and section 6.6.1 (an intermediary can relabel the signature but not the covered `Signature-Agent` key). The origin-based allowlist trust rule, fetch limits, and the bare-origin handling above are this verifier's policy; the bare-origin rule is a stated deviation from sections 4.1 and 4.4.

Not implemented: verifying the directory response's own signature (-01 Appendix B: RECOMMENDED for directory servers, proves possession of each advertised key and binds the key set to its authority). Appendix B.1 lets a verifier use a key it obtained by resolving the directory itself whether or not it has valid proof, so fetching over HTTPS from an allowlisted URL is the trust anchor here, and the proof is only needed to attribute redistributed material, which this verifier never does (`fetched=False` keys carry no URL). Mention this if the user needs stronger guarantees.

**Test keys and directory limits.** Known test keys must not be used in production and verifiers SHOULD reject them (-01 section 6.8). `parse_directory` and the resolvers drop JWKs whose thumbprint is in `TEST_KEY_THUMBPRINTS` unless `allow_test_keys=True`: the RFC 9421 Appendix B.1.4 key (also the -01 examples), the RFC 8037 Appendix A.1 key, and this skill's two vector keys (`generate_vectors.KEY` and `OTHER`). The list is not exhaustive (-01 says "including"). `StaticKeyResolver` raises `ValueError` naming the thumbprint if its configuration contains one. Ports and tests that use the bundled vectors pass `allow_test_keys=True`. A directory with more than `max_keys` (64) entries, counted before filtering, or one that is not a JWKS (a JSON object with a `keys` array) raises `ValueError`; the resolver treats it as a discovery failure and keeps its last good copy.

## 2. Request binding — `require_binding` (default False)

-01 section 5.2 requires only one of `@authority` or `@target-uri` to be signed, plus `created`, `expires`, `keyid` and `tag`, and says that signature binds an authority, not a request. The verifier also requires a present `Signature-Agent` header to be covered under the signature's label (section 5.2.1), and many agents sign only those two. A signature like that proves who sent *a* request to this host, but not which method, path or body. No component covers the body: an agent that needs it covered must send and cover `Content-Digest`, which the verifier then checks against the bytes received. `@target-uri` counts as covering path and query for `binds_request`.

- **Off (default):** such signatures verify with `binds_request=False`. Recommended handling: admit them for safe methods only.
- **On:** they become `invalid` (blocked). Choose this only if the user controls or negotiates with the agents they accept, or the endpoint is state-changing only.

## 3. Nonces — `require_nonce` (default False)

Without a nonce, a captured request can be replayed until it goes stale (`max_age`). With TLS, capture usually means a compromised intermediary or leaked logs, so the risk is real but narrow.

- **Off (default):** no-nonce signatures verify with `replay_protected=False`.
- **On:** they become `invalid`. Reasonable for APIs whose agent clients you onboard.

`min_nonce_length` (16) rejects trivially guessable nonces. It is this verifier's local policy: -01 section 5.2.3 defines no nonce requirements beyond RFC 9421 section 7.2.2, and -01 Appendix C.6 leaves enforcement to deployment policy.

## 4. Freshness — `max_age` 300 s, `max_lifetime` 86400 s, `clock_skew` 5 s

- `max_age`: maximum age of `created`. This bounds replay for nonce-less signatures and the nonce cache's size for all signatures, independent of how far out the agent set `expires`. Lowering it below ~60 s starts rejecting agents with slow clocks or queued requests.
- `max_lifetime`: maximum `expires - created`. -01 section 5.2 recommends 24 h or less, and section 6.9 warns that long windows increase replay risk and that a reusable static signature has bearer-token semantics.
- `clock_skew`: tolerance in both directions. Keep it small; agents with drifting clocks should fix them.

## 5. Nonce store failure — `fail_closed_methods` (POST, PUT, PATCH, DELETE)

If the shared store is unreachable, state-changing requests become `invalid`, and safe ones verify with `replay_protected=False`. Ask if the user would rather fail closed for everything.

## 6. Actions per outcome

Start from the table in SKILL.md. Points to raise:

- `invalid`, `expired`, `replay`: block. Log them; spikes per operator suggest key compromise or an attack.
- An unsigned request whose User-Agent claims to be a known signing agent is suspicious. Feed that into existing bot scoring.
- `verified` says nothing about the end user. Sensitive actions still need the user's session or a user-granted token, and rate limits should apply per operator *and* per user.

### Custom resolvers

The verifier always gets the key and its trust flags from `resolve(keyid, operator, now)`, so a subclass, wrapper or instance-patched `resolve` can revoke keys or downgrade trust. The contract:

- `operator` (also passed to `is_allowlisted` and `directory_unavailable`) is a **normalized identifier** (the output of `normalize_agent_url`, query dropped), not an origin as in 0.1.1, or `None` when the request has no usable `Signature-Agent` (absent, or an ignored member, section 1). Update resolvers written against 0.1.1 accordingly.
- `ResolvedKey(key, trusted, attributed=True)`. The Verifier reports `verified` only when `trusted and attributed`. `attributed=False` means the key is tied to no URL (it came from a list, or from a source that did not resolve the claimed URL): the Verifier then forces the outcome to `signed_untrusted` and `Result.operator` to `None`, whatever `trusted` says, so the request is identified by `keyid` (-01 section 4.3). `attributed=True, trusted=False` is `signed_untrusted` with `operator` set to the claimed URL; use it only for a key you did obtain by resolving that URL. A resolver that returns `ResolvedKey(key, trusted)` keeps the old behaviour. Never attribute a key to a URL because the client asserted it (-01 section 5.4: lookup is on the (URL, key) pair).
- `directory_unavailable(operator, now) -> bool` is optional, looked up with `getattr`, and must be side-effect free: no fetch and no mutation. The Verifier asks it only after `resolve()` returned `None`; `DirectoryKeyResolver.resolve` also uses it to decide whether the unattributed lists may be consulted (removal wins). `True` turns the miss into `unknown_operator` (`key directory unavailable`) instead of `invalid`; it can never yield a key or trust. `DirectoryKeyResolver` answers `True` for an allowlisted identifier with no fresh cached directory, because an expired copy cannot rule out a rotated key that we failed to fetch.
- A custom `resolve` that revokes a key and returns before calling `super().resolve()` never fills the cache, so on a cold cache the result is `unknown_operator` (`key directory unavailable`), not `invalid`, and it stays that way until another request warms the cache and again after each cache expiry. Revoking resolvers should call `super().resolve()` first and then filter its result.
- Reasons: when no key is found for an allowlisted identifier whose keyid is one of `TEST_KEY_THUMBPRINTS`, the reason is `known test key rejected`. This is decided from the keyid alone, so with `allow_test_keys=True` an unknown test key (one not in the directory) can carry that reason too; the outcome is unchanged (`invalid`).
